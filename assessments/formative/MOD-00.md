# MOD-00 Contract Evidence and Release Discipline

## Read-only formative check
Use this reflection to inspect reasoning only. It awards nothing, authorizes nothing, and makes no assessment or runtime claim.

## Must-pass invariants
1. Keep documentation, exact artifacts, runtime observations, project methods, learner/evaluator results, and production qualification on separate evidence axes; never promote one into another.
2. Bind every claim to a precise envelope—surface, artifact or page, versions, backend, topology, target, date, and classification—or narrow it, open a discrepancy, or retain `unknown-not-tested`.
3. Fail closed when evidence, authority, target identity, or effect state is missing; never infer execution from static checks or retry an uncertain consequential effect blindly.

## Worked response: strong versus weak
**Prompt:** Declarations expose an option, but source validation narrows it for one backend. What may be stated?

**Strong:** “For the exact 0.8.9/0.32.11 static lane, the option is exported, while backend-specific source narrows acceptance. Record the discrepancy and teach only the safe subset. No live acceptance is claimed; target behavior remains `unknown-not-tested`.”

**Weak:** “The SDK supports the option because TypeScript exposes it.”

The strong response identifies evidence class, tuple, scope, discrepancy treatment, and non-claim. The weak response promotes public shape into runtime behavior.

## Misconception indicators
- Calling a compile, fixture, lesson, or canary “production-ready.”
- Using “latest” without an evidence cutoff.
- Averaging conflicting sources or treating a docs index as proof of every linked page.
- Treating a project controller rule as a built-in Letta guarantee.

## Continue or revisit
**Continue** if you can produce a claim-and-shadow pair, preserve unknowns, and explain why identical artifact bytes can remain separate evidence lanes. **Revisit** if you collapse status axes or cannot state the fail-closed disposition.
