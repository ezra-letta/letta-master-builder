# MOD-03 Capability Topology and Model Selection

## Read-only formative check
Use this reflection to inspect selection reasoning only. It awards nothing, authorizes nothing, and makes no assessment or runtime claim.

## Must-pass invariants
1. Select from mission requirements and ownership boundaries: distinguish capability, surface, backend, topology, client entry point, execution host, state host, computer, provider, and model configuration scope.
2. Preserve the curriculum lane—Agent SDK root entry point, TypeScript on trusted Node, Local as primary, Cloud as contrast—and treat alternatives as selection literacy unless a requirement and evidence justify another surface.
3. Choose the smallest defensible safe subset; package shape or documentation never establishes target entitlement, catalog availability, backend parity, model equivalence, or observed lifecycle behavior.

## Worked response: strong versus weak
**Prompt:** The preferred model handle is rejected, and an operator proposes a similarly named model.

**Strong:** “Pause selection, preserve the prior decision, and under separate authority inspect the target-scoped catalog. Compare context, tool use, modalities, latency, cost, provider restrictions, reasoning behavior, and intended configuration scope. Substitute only when the recorded fallback policy permits capability equivalence; quality remains unevaluated.”

**Weak:** “Use the newer model from the same family; it should be compatible.”

The strong response treats availability, suitability, and scope as separate. The weak response infers equivalence from naming.

## Misconception indicators
- Assuming Cloud includes local files, connected computers, sandboxes, providers, or credentials.
- Treating root and portable client entry points as interchangeable.
- Choosing direct protocol because it exposes more controls without assigning lifecycle duties.
- Using a one-shot query as persistent-agent architecture.

## Continue or revisit
**Continue** if you can defend the selected surface, map every host and trust edge, and state what remains unknown. **Revisit** if backend labels replace topology details or model names replace capability requirements.
